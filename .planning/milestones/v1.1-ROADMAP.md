## Phase Details

### Phase 7: CSS Foundation & App Shell
**Goal**: The app renders correctly with Mary UI as the sole CSS system — Flux CSS is gone, the layout shell uses Mary UI components, and the globally-persisted audio player uses Mary UI icons
**Depends on**: Nothing (first v1.1 phase)
**Requirements**: INFRA-01, INFRA-02, INFRA-03, LAYOUT-01, LAYOUT-02, LAYOUT-03, LAYOUT-04, PLAYER-01, PLAYER-02
**Success Criteria** (what must be TRUE):
  1. Authenticated pages load without visual breakage caused by competing CSS custom properties from Flux and daisyUI
  2. The sidebar and main content area render using `x-mary-main` with named slots — navigation links appear and are clickable
  3. The user menu dropdown opens and closes correctly using a Mary UI dropdown component
  4. Audio player play/pause/skip controls display correct icons from Heroicons via `x-mary-icon` (no broken icon placeholders)
  5. Volume and seek sliders are styled with daisyUI range classes and remain fully functional
**Plans**: 3 plans

Plans:
- [ ] 07-01-PLAN.md — CSS cleanup: remove Flux-specific rules and add Mary UI @source directive
- [ ] 07-02-PLAN.md — Audio player: replace Flux icons with Mary UI icons and restyle sliders with daisyUI
- [ ] 07-03-PLAN.md — Layout shell: migrate sidebar, header, user menu, and bottom nav to Mary UI

### Phase 8: Shared Components & Modal Pattern
**Goal**: The auth layout and all shared components are migrated to Mary UI, and the Mary UI modal pattern (Livewire boolean property + `wire:model`) is established in the codebase
**Depends on**: Phase 7
**Requirements**: LAYOUT-05, MODAL-01, MODAL-02
**Success Criteria** (what must be TRUE):
  1. Auth pages (login, register, forgot-password) render correctly using the Mary UI auth layout with no Flux wrappers
  2. Any modal in the app opens and closes via a Livewire boolean property (not a Flux named event) — verified on at least one modal
  3. The "add to playlist" modal is a single modal instance driven by a `selectedTrackId` property — it opens correctly for any track without rendering N modal elements
**Plans**: 2 plans

Plans:
- [ ] 08-01-PLAN.md — Auth layout: restyle simple.blade.php with daisyUI card and delete dead layouts
- [ ] 08-02-PLAN.md — AddToPlaylistModal: create Livewire component with Mary UI modal pattern, update triggers, delete old Blade modal

### Phase 9: Page Migration
**Goal**: All five authenticated content pages are fully migrated to Mary UI — no Flux components remain in library, album, upload, playlist, or profile views
**Depends on**: Phase 8
**Requirements**: PAGE-01, PAGE-02, PAGE-03, PAGE-04, PAGE-05
**Success Criteria** (what must be TRUE):
  1. The library index page displays tracks and albums using Mary UI components with functional search
  2. The album show page displays tracks with correct play actions using Mary UI buttons and icons
  3. The upload summary page renders upload results using Mary UI components
  4. Playlist pages (index, show, create, edit) render and function correctly — creating a playlist and adding a track works end-to-end
  5. The profile show page displays user info, avatar, bio, and stats using Mary UI components
**Plans**: 3 plans

Plans:
- [ ] 09-01-PLAN.md — UploadModal Livewire component, empty-state Blade component, and test suite
- [ ] 09-02-PLAN.md — Library index, album show, and upload summary page migration
- [ ] 09-03-PLAN.md — Playlist pages (index, show, create, edit) and profile show page migration

### Phase 10: Settings Migration
**Goal**: All settings pages are migrated to Mary UI — the settings sub-layout, profile, password, appearance, two-factor, users, and account deletion pages all use Mary UI exclusively
**Depends on**: Phase 9
**Requirements**: SETTINGS-01, SETTINGS-02, SETTINGS-03, SETTINGS-04, SETTINGS-05, SETTINGS-06, SETTINGS-07, SETTINGS-08
**Success Criteria** (what must be TRUE):
  1. Settings navigation renders correctly via Mary UI — switching between settings sections works
  2. Profile and password settings forms submit and save without errors using Mary UI form inputs
  3. The appearance settings page has a working theme toggle that writes `data-theme` to the `<html>` element without referencing `$flux.appearance`
  4. Two-factor authentication setup and recovery codes pages render correctly — OTP input accepts codes
  5. Admin users page displays the user list and invite functionality using Mary UI components
**Plans**: 4 plans

Plans:
- [ ] 10-00-PLAN.md — Wave 0: Create test stubs for settings navigation, appearance, users, and auth pages
- [ ] 10-01-PLAN.md — Settings layout, heading partial, profile, password, and delete account migration
- [ ] 10-02-PLAN.md — Appearance theme toggle (DB-backed) and two-factor/recovery codes migration
- [ ] 10-03-PLAN.md — Admin users page and auth pages (confirm-password, 2FA challenge, verify-email)

### Phase 11: Flux Removal & Cleanup
**Goal**: The `livewire/flux` package is removed from the codebase — no Flux component, directive, CSS, or magic property reference survives in any blade file
**Depends on**: Phase 10
**Requirements**: CLEAN-01, CLEAN-02, CLEAN-03, CLEAN-04
**Success Criteria** (what must be TRUE):
  1. A full codebase grep for `flux:`, `@flux`, `@fluxScripts`, `@fluxAppearance`, and `$flux.` returns zero results
  2. `composer remove livewire/flux` completes without errors and the package is absent from `composer.json`
  3. All 30 blade files pass a Flux-free audit — the application boots and all routes return 200 with no `BadMethodCallException`
  4. The full Pest test suite passes after Flux removal
**Plans**: 2 plans

Plans:
- [ ] 11-01-PLAN.md — Remove all Flux references from blade templates, CSS, and uninstall composer package
- [ ] 11-02-PLAN.md — Invert test assertions, add Flux-free audit test, clean project instruction files
