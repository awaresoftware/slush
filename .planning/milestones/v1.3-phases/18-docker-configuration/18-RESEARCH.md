## Summary

This phase builds a complete Docker Compose setup using the already-installed `laravel/sail ^1.41` dependency. The key deliverables are: a hand-crafted `compose.yaml` (not generated by `sail:install`), a bash entrypoint script at `docker/start.sh`, and a `.env.docker.example` file. All three components work together so users can run `sail up -d` and have a fully functional application.

The Sail runtime Dockerfiles live at `vendor/laravel/sail/runtimes/8.4/` and are used as-is without publishing — the project references them directly in the `build.context` block. The existing Sail stubs (`compose.stub`, `mysql.stub`, `redis.stub`) are the canonical source for service configuration, healthcheck syntax, and image versions. They must be read and adapted rather than invented from scratch.

The most technically nuanced decision is D-05 (conditional music volume mount). Docker Compose does not support conditional volume inclusion natively. The recommended approach is a `compose.music.yaml` override file: users who want the music mount copy that file to `compose.override.yaml` and set `MUSIC_LIBRARY_PATH`. Docker Compose automatically picks up `compose.override.yaml` on every `docker compose up` run — no extra flags needed.

**Primary recommendation:** Hand-craft `compose.yaml` using the verified Sail stubs as templates, add a `docker/start.sh` entrypoint for first-run setup, and use the `compose.override.yaml` pattern for the optional music volume.

## Architecture Patterns

### Recommended Project Structure

```
/
├── compose.yaml              # Main Docker Compose definition (web, mysql, redis, worker)
├── compose.music.yaml        # Template override file — copy to compose.override.yaml to enable music mount
├── docker/
│   └── start.sh              # Custom entrypoint: runs migrate, optional npm build, then starts supervisord
├── .env.docker.example       # Standalone Docker env file — copy to .env to use with Docker
```

### Pattern 1: Sail PHP 8.4 Build Context

The `laravel.test` service builds from Sail's vendored Dockerfile rather than a custom one. The PHP version is controlled by `build.context`:

**What:** Reference the vendored Sail runtime via `context: ./vendor/laravel/sail/runtimes/8.4`.
**When to use:** Every project using Sail without `sail:publish`. Avoids maintaining a custom Dockerfile while getting all Sail's bundled extensions.

```yaml
# Source: vendor/laravel/sail/stubs/compose.stub
services:
    laravel.test:
        build:
            context: ./vendor/laravel/sail/runtimes/8.4
            dockerfile: Dockerfile
            args:
                WWWGROUP: '${WWWGROUP}'
        image: sail-8.4/app
        extra_hosts:
            - 'host.docker.internal:host-gateway'
        ports:
            - '${APP_PORT:-80}:80'
        environment:
            WWWUSER: '${WWWUSER}'
            LARAVEL_SAIL: 1
        volumes:
            - '.:/var/www/html'
        networks:
            - sail
```

### Pattern 2: Custom Entrypoint via `command` Override

The Sail image's default `ENTRYPOINT` is `/usr/local/bin/start-container`. That script:
1. Optionally remaps the `sail` user UID to match `$WWWUSER`
2. If given arguments, runs them as the sail user via `gosu`
3. If given no arguments, launches supervisord

Use `command` in `compose.yaml` to pass the custom setup script as an argument to the entrypoint, which runs it as the `sail` user:

```yaml
# Source: vendor/laravel/sail/runtimes/8.4/start-container (read and verified)
services:
    laravel.test:
        # ... build and image config above ...
        command: ["/bin/bash", "/var/www/html/docker/start.sh"]
```

The `docker/start.sh` script runs setup steps then exec-replaces itself with supervisord:

```bash
#!/usr/bin/env bash
set -e

# Run migrations on every boot (idempotent, picks up new migrations after git pull)
php artisan migrate --force

# Build assets only when the manifest is missing (skip on subsequent restarts)
if [ ! -f /var/www/html/public/build/manifest.json ]; then
    npm install
    npm run build
fi

# Create storage symlink (idempotent with --force)
php artisan storage:link --force

# Hand off to supervisord (starts PHP web server via Sail's supervisord.conf)
exec /usr/bin/supervisord -c /etc/supervisor/conf.d/supervisord.conf
```

### Pattern 3: Dedicated Worker Service (Reuses App Image)

The worker is a second container from the same image, with a different `command`. It shares the same code volume and environment. It does NOT need to run the entrypoint setup steps (migrations will have already run in the web container, which starts first due to `depends_on`):

```yaml
# Source: pattern verified in virendra.dev article and serversideup.net docs
services:
    worker:
        image: sail-8.4/app                   # Same image as laravel.test
        command: ["php", "artisan", "queue:work", "--sleep=3", "--tries=3", "--max-time=3600"]
        volumes:
            - '.:/var/www/html'
        networks:
            - sail
        depends_on:
            laravel.test:
                condition: service_started
            mysql:
                condition: service_healthy
            redis:
                condition: service_healthy
        restart: unless-stopped
        environment:
            WWWUSER: '${WWWUSER}'
            LARAVEL_SAIL: 1
```

### Pattern 4: Healthchecks and `depends_on: condition: service_healthy`

Both MySQL and Redis already have healthchecks in Sail's stubs. The `laravel.test` service adds `depends_on` in long form:

```yaml
# Source: vendor/laravel/sail/stubs/mysql.stub and redis.stub (read and verified)
services:
    laravel.test:
        depends_on:
            mysql:
                condition: service_healthy
            redis:
                condition: service_healthy

    mysql:
        image: 'mysql:8.4'
        healthcheck:
            test: ["CMD", "mysqladmin", "ping", "-p${DB_PASSWORD}"]
            retries: 3
            timeout: 5s

    redis:
        image: 'redis:alpine'
        healthcheck:
            test: ["CMD", "redis-cli", "ping"]
            retries: 3
            timeout: 5s
```

**Critical:** MySQL initialization (creating databases, running `docker-entrypoint-initdb.d` scripts) takes 20-60 seconds on first boot. Add `start_period: 30s` to the MySQL healthcheck to avoid premature failure:

```yaml
    mysql:
        healthcheck:
            test: ["CMD", "mysqladmin", "ping", "-p${DB_PASSWORD}"]
            retries: 5
            timeout: 5s
            interval: 10s
            start_period: 30s
```

### Pattern 5: Conditional Music Volume via Override File

Docker Compose does not support if/else logic in volume definitions. Environment variable interpolation in volumes (`${MUSIC_LIBRARY_PATH}:/music`) causes a fatal parse error when the variable is empty — it does not silently skip the mount.

**Correct approach:** Ship a `compose.music.yaml` template in the repository. Users who want the music mount:
1. Copy `compose.music.yaml` to `compose.override.yaml`
2. Set `MUSIC_LIBRARY_PATH=/path/to/music` in `.env`

Docker Compose automatically merges `compose.override.yaml` into `compose.yaml` on every `docker compose up` without any flags:

```yaml
# compose.music.yaml (ship this; user copies to compose.override.yaml)
# Source: docs.docker.com/compose/how-tos/multiple-compose-files/merge/
services:
    laravel.test:
        volumes:
            - '${MUSIC_LIBRARY_PATH}:/music:ro'
    worker:
        volumes:
            - '${MUSIC_LIBRARY_PATH}:/music:ro'
```

### Anti-Patterns to Avoid

- **Using `sail:install` to generate `compose.yaml`:** The generated file includes Selenium and Mailpit (excluded by D-06) and uses `--php=8.5` default. Hand-craft instead.
- **Inline `if [ -n "$MUSIC_LIBRARY_PATH" ]` volume mount in entrypoint:** Docker volume mounts are declared at container start, not inside the container. The entrypoint can only see the mount point; it cannot add mounts dynamically.
- **`${MUSIC_LIBRARY_PATH:-/dev/null}:/music` workaround:** Mounting `/dev/null` as a directory causes errors. The override file pattern is cleaner and documented.
- **Using short `depends_on` syntax for healthchecks:** `depends_on: [mysql, redis]` only waits for the container to start, not for it to be healthy. Use long form with `condition: service_healthy`.
- **Running `npm install` on every boot:** D-03 explicitly requires the manifest check. Unconditional npm installs add 30-60 seconds to every restart.
- **Defining `VITE_PORT` in `.env.docker.example`:** The Vite dev server does not run in Docker (assets are pre-built via `npm run build`). Including it causes confusion.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| PHP 8.4 Docker image with extensions | Custom Dockerfile | `vendor/laravel/sail/runtimes/8.4/Dockerfile` via build context | Already installs php8.4-mysql, php8.4-redis, php8.4-gd, nodejs, npm, composer; battle-tested |
| MySQL healthcheck | Custom TCP probe script | `mysqladmin ping` (already in mysql.stub) | Reliable, minimal, already in Sail's own stub |
| Redis healthcheck | Custom script | `redis-cli ping` (already in redis.stub) | Built into redis:alpine image |
| MySQL testing database creation | Manual SQL in entrypoint | `vendor/laravel/sail/database/mysql/create-testing-database.sh` mount | Sail ships this; mounts via docker-entrypoint-initdb.d |
| User UID remapping | Manual `usermod` in entrypoint | Sail's own `start-container` script handles this via `WWWUSER` env var | The existing entrypoint already calls `usermod -u $WWWUSER sail` |

**Key insight:** Sail's vendored runtime already handles the hard parts (extensions, user management, supervisord). The custom work is the entrypoint setup sequence and the compose.yaml topology.

## Common Pitfalls

### Pitfall 1: MySQL First-Boot Race Condition

**What goes wrong:** The `laravel.test` container starts, the entrypoint runs `artisan migrate --force`, but MySQL is still initializing its data directory. Migration fails with "Connection refused" or "Host 'laravel.test' is not allowed to connect."

**Why it happens:** `depends_on: condition: service_healthy` waits for the healthcheck to pass, but MySQL's healthcheck (`mysqladmin ping`) can succeed before the `docker-entrypoint-initdb.d` scripts finish creating the application database.

**How to avoid:** Add `start_period: 30s` and `interval: 10s` with `retries: 5` to the MySQL healthcheck. This gives MySQL enough time to complete initialization before the healthcheck starts counting failures.

**Warning signs:** Migration errors on first `sail up` that succeed on second `sail up`.

### Pitfall 2: Empty `MUSIC_LIBRARY_PATH` Causing Compose Parse Error

**What goes wrong:** If `volumes: - '${MUSIC_LIBRARY_PATH}:/music'` is in the main `compose.yaml` and `MUSIC_LIBRARY_PATH` is not set, Docker Compose 2.x raises a fatal error: "variable is not set" or produces a mount with an empty source path.

**Why it happens:** Docker Compose v2 treats empty bind mount source paths as errors (unlike older v1 behavior of silently ignoring them).

**How to avoid:** Never put the music volume in the main `compose.yaml`. Use the override file pattern (D-05). The variable is only evaluated when `compose.override.yaml` is present.

**Warning signs:** `docker compose config` errors or `bind source path does not exist` errors on `sail up`.

### Pitfall 3: Worker Container Runs Migrations Concurrently

**What goes wrong:** Both `laravel.test` and `worker` run the entrypoint setup script, causing duplicate migration attempts and potential race conditions.

**Why it happens:** If the worker uses the same `command` as the web container.

**How to avoid:** The worker's `command` is `php artisan queue:work ...` directly — it does NOT call `docker/start.sh`. By the time the worker starts (it `depends_on: laravel.test: condition: service_started`), migrations will have already run.

**Warning signs:** Database errors in worker logs on first boot.

### Pitfall 4: `WWWGROUP`/`WWWUSER` Not Set

**What goes wrong:** The Sail Dockerfile requires `WWWGROUP` as a build arg. If it is not set when building, the `sail` group is created with group ID 0 (root), causing permission issues.

**Why it happens:** These variables are set by the `sail` binary at runtime from the host system, but must also be present in `.env.docker.example` with sensible defaults.

**How to avoid:** Set `WWWGROUP=1000` and `WWWUSER=1000` in `.env.docker.example`. Most Linux/macOS systems use UID/GID 1000 for the primary user.

**Warning signs:** Permission denied errors on storage writes, or Sail image build failures.

### Pitfall 5: Test Suite MySQL Compatibility

**What goes wrong:** The test suite passes on SQLite but a migration fails on MySQL due to syntax differences.

**Why it happens:** The test suite uses `DB_CONNECTION=sqlite` and `DB_DATABASE=:memory:` from `phpunit.xml`. Migrations are never tested against MySQL as part of the standard test run.

**How to avoid:** Audit all migrations for SQLite-only patterns before shipping. Specifically: no raw SQL with SQLite-specific pragmas, no `json` column type assertions that differ between engines, no reliance on implicit INTEGER primary keys as rowid. The existing migrations have been reviewed — they use standard Eloquent Blueprint methods with no engine-specific syntax.

**Warning signs:** Migration failures inside the container on first `sail up` that do not reproduce with `php artisan test`.

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| `docker-compose.yml` | `compose.yaml` | Docker Compose v2 (2022) | Sail now generates `compose.yaml`; use this filename |
| `depends_on: [mysql]` (container started) | `depends_on: mysql: condition: service_healthy` | Docker Compose 3.9 spec | Actual health gate, not just container start |
| `version: "3"` header | No version header | Docker Compose v2 spec | `version` field is deprecated; omit it |
| Supervisord inside single container for all processes | Separate Docker Compose services per process | Industry standard 2022+ | Sail D-11 decision aligns with this |
| `mysql_native_password` auth plugin | `caching_sha2_password` (default in MySQL 8.4) | MySQL 8.4 (2024) | PHP 8.4 mysqlnd supports it natively; no workaround needed |

**Deprecated/outdated:**
- `version: "3.8"` YAML header: deprecated in Docker Compose v2 spec; Sail's own stubs omit it
- `mysql_native_password` env var override: no longer needed with PHP 8.4 + MySQL 8.4
- `docker-compose.yml` filename: valid but Sail now defaults to `compose.yaml`

## Open Questions

1. **`APP_KEY` in Docker environment**
   - What we know: The entrypoint script runs `artisan migrate --force` but not `artisan key:generate`. Without `APP_KEY`, Laravel will fail on boot.
   - What's unclear: Should the entrypoint auto-generate the key if missing, or should `.env.docker.example` require users to set it manually?
   - Recommendation: Add `php artisan key:generate --force` to `docker/start.sh` as the first step, protected by the same `preg_match` guard used in the native setup script. Alternatively, document that users must run `sail artisan key:generate` after first boot.

2. **`sail` binary permissions on Windows**
   - What we know: `WWWUSER`/`WWWGROUP` defaults of 1000 work for Linux/macOS. Windows Docker Desktop uses a different UID mapping.
   - What's unclear: Whether Windows users will hit permission issues with the default values.
   - Recommendation: Document in `.env.docker.example` comments that Windows users may need `WWWUSER=0` and `WWWGROUP=0` (run as root inside container), which is the Sail default for Windows.
