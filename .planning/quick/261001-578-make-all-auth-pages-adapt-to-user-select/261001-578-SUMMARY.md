# Quick 261001-578: Guest Appearance on Auth Pages Summary

**Two long-lived appearance cookies plus a `fromCookie()` fallback in `Theme`/`Accent`, so every auth page paints in the visitor's own theme and accent with no auth view, layout or stylesheet changed**

## Performance

- **Duration:** 7 min
- **Started:** 2026-10-01T01:58:59Z
- **Completed:** 2026-10-01T02:06:11Z
- **Tasks:** 2
- **Files modified:** 5

## Accomplishments

- The appearance preference now survives into signed-out sessions. `Theme::forUser()` and `Accent::forUser()` read the user record first, then a five-year cookie, then the default — so a guest sees their own theme on the login page instead of plain white with red buttons.
- Every auth page inherits it for free. Both `layouts/guest` (login, register, forgot-password, reset-password) and `layouts/auth/simple` (confirm-password, two-factor, verify-email) already call `partials.html-attributes` and `partials/head`, so the fix is one shared layer and **zero** view, layout or stylesheet edits.
- Correct on first paint, not corrected by JavaScript after hydration: the server paints `data-theme`/`data-accent` and the theme-color meta.
- The trust boundary holds. A hand-edited cookie resolves through `self::tryFrom()` — the same allowlist the `Rule::in` validation uses — so an unrecognised value falls back to the system theme and default accent instead of reaching the attribute.
- Nine regression cases added, and their teeth confirmed by mutation check (below).

## Decisions Made

- **Record before cookie, in both enums.** Keeping the user record first is what makes the change additive: a signed-in user's settings page and app pages are unaffected, and the cookie is only ever consulted when there is no record to read. Threat T-261001578-03 (stale cookie vs. current preference) is therefore accepted by design rather than mitigated.
- **`tryFrom` over any hand-rolled validation.** It is the identical allowlist that `values()` and the Livewire `Rule::in` already enforce, so the read and write trust boundaries are provably the same list. No config entry, migration, cast, or dependency was added.
- **The plan's five-year lifetime is asserted, not just implemented.** The whole point is surviving into signed-out sessions, and a session-scoped cookie would pass a value-only assertion while quietly breaking the feature across browser restarts. One extra assertion on `getExpiresTime()` guards it.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `Cookie::getQueuedCookies()` is not name-keyed, so the plan's read instruction could not work**
- **Found during:** Task 2
- **Issue:** The plan's context block states trap #2 as "returns a plain array keyed by cookie name... Use `$queued[Theme::COOKIE]`". It returns a plain array, but `Arr::flatten()` builds it with `$result[] = $item`, which **discards the original keys** — the result is numerically indexed (`array_keys()` returned `[0, 1]`). `$queued[Theme::COOKIE]` therefore always raises `Undefined array key "foonk_appearance_theme"`. The trap's stated *symptom* (`->get()` throwing "Call to a member function get() on array") is real, but the recommended fix does not address the actual key loss.
- **Fix:** `collect(Cookie::getQueuedCookies())->keyBy(fn ($cookie) => $cookie->getName())` restores the name lookup. The queue itself was never flushed by middleware — my first reading of the `Undefined array key` error as a flush was wrong, and the diagnostic settled it.
- **Files modified:** `tests/Feature/Settings/AppearanceSettingsTest.php`
- **Verification:** Both save cases pass; the rejected-save case confirms the queue really is empty when nothing should be written, so `toBeEmpty()` is meaningful and not vacuous.
- **Committed in:** `cf2774e`
- **Note:** The inlined `keyBy` one-liner was preferred over a `tests/Pest.php` helper, which would have taken the diff outside the plan's declared `files_modified` set for two call sites.

**2. [Rule 1 - Bug] Login-page tests 302-redirected instead of rendering**
- **Found during:** Task 2
- **Issue:** `RequireNoUsers` (appended to the `web` group) redirects `login` → `register` while no users exist. Under `RefreshDatabase` each test starts with an empty database, so a guest test that creates no user received a redirect stub whose body is a bare `<html>` and no `data-accent` at all — the assertions failed in a way that looked like a broken attribute partial.
- **Fix:** Create a user in the four login-page cases, matching the existing case in the same file, with a comment naming the middleware. `password.request` needed no user because the middleware only special-cases the login route names.
- **Files modified:** `tests/Feature/AuthLayoutTest.php`
- **Verification:** The two guest-render cases pass on real markup; `RequireNoUsers` confirmed as the only redirect source via a throwaway diagnostic test (since removed).

**3. [Rule 2 - Missing Critical] Existing guest case carried a premise that is no longer true**
- **Found during:** Task 2
- **Issue:** `renders no data-theme attribute for guests, who follow the system theme` — planned, and handled as the plan specified: renamed to state that a guest with *no appearance cookie* follows the system theme. Both assertions were left byte-identical, as were the signed-in-user, system-theme and theme-color cases that form the "record still wins" regression net.
