<objective>
Make the appearance preference survive into signed-out sessions so every auth page renders in the visitor's chosen theme and accent.

Purpose: the auth pages are already fully theme-token based and correct — the bug is that the preference lives only on the `User` record, and `partials/html-attributes.blade.php` resolves it with `auth()->user()`, which is null on every auth page. So the theme silently degrades to `System` (plain white) and the accent to `MusicRed` (red buttons) exactly when someone is trying to log in. The preference needs a guest-readable copy.

Output: Two long-lived appearance cookies written on save, and a cookie fallback in the two enums that every layout already resolves through. No auth view, layout, or stylesheet is touched.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Browser cookie → server render | A client-supplied, attacker-editable cookie value is read during an unauthenticated request and written into the `data-theme` and `data-accent` attributes of the `<html>` element. This is a new boundary: before this change the only appearance input was a server-side `User` column. |
| Livewire save request → appearance cookies | The appearance component writes the cookie values. Its `Rule::in(Theme::values())` / `Rule::in(Accent::values())` validation is the gate, and the write happens only on the path that passed it. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-261001578-01 | Tampering | `Theme::fromCookie()` / `Accent::fromCookie()` → `data-theme`, `data-accent` in `partials/html-attributes.blade.php` | high | mitigate | Resolve the cookie through `self::tryFrom(...)`, whose allowlist is `self::cases()` — the identical list the Livewire validation uses — so an unrecognised value becomes `self::System` / `self::MusicRed` and never reaches the attribute. `EncryptCookies` additionally signs and encrypts the cookie and nulls it when it cannot be decrypted, so a forged value arrives as null and hits the same default. Only the enum's own `->value` is interpolated, and Blade's `{{ }}` escaping applies on top. |
| T-261001578-02 | Tampering | `persist()` in `resources/views/pages/settings/⚡appearance.blade.php` | high | mitigate | Queue the cookies only after `Auth::user()->update($validated)` succeeds, on the success path exclusively. The `ValidationException` branch returns before the write, so an unvalidated slug can never be persisted to a cookie. |
| T-261001578-03 | Spoofing | Stale cookie vs. the user's current stored preference | low | accept | Accepted by design: `forUser()` reads the user record first, so a signed-in user is never affected by a stale cookie, and a guest has no record to spoof. | T-261001578-04 | Information Disclosure | Cookie contents | low | accept | Accepted: the cookie holds one theme slug and one accent slug, both already visible in the page markup as `data-theme` / `data-accent`. Encrypting them adds tamper protection but hides nothing that is not already public. |
